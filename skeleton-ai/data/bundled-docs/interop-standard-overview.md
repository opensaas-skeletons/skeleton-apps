# Interop Standard Overview

## What is the Interop Standard?

The Open SaaS Skeletons Interop Standard is a data portability specification implemented by each skeleton application. It provides a consistent pattern for exporting and importing data as portable JSON payloads, ensuring no vendor lock-in and enabling data migration between compatible applications.

## Common Pattern

Every skeleton app implements the same interop pattern:

### Export Endpoint
```
GET /api/export
```
Returns a JSON payload containing all application data in a portable format. Internal IDs are either stripped or replaced with human-readable references (titles, names) to ensure portability across different databases.

### Import Endpoint
```
POST /api/import
Content-Type: application/json
```
Accepts a JSON payload and creates new records. Generates fresh UUIDs, resolves references, and maintains referential integrity.

### Payload Structure
Every export payload includes:
```json
{
  "version": "1.0",
  "app": "skeleton-{name}",
  "exported_at": "ISO 8601 timestamp",
  // ... app-specific data
}
```

## Per-App Standards

### Skeleton Tasks — Task Standard v1.0
Exports boards with columns and tasks. Tasks reference columns by title (not ID) for portability.
```json
{
  "version": "1.0",
  "app": "skeleton-tasks",
  "boards": [{ "title": "...", "columns": [{ "title": "...", "tasks": [...] }] }]
}
```

### Skeleton Automation — Automation Standard v1.0
Exports workflows with nodes and connections.
```json
{
  "version": "1.0",
  "app": "skeleton-automation",
  "workflows": [{ "name": "...", "nodes": [...], "connections": [...] }]
}
```

### Skeleton Database — Database Standard v1.0
Exports table schemas and row data.
```json
{
  "version": "1.0",
  "app": "skeleton-database",
  "tables": [{ "name": "...", "columns": [...], "rows": [...] }]
}
```

### Skeleton Wiki — Wiki Standard v1.0
Exports workspaces with pages and version history.
```json
{
  "version": "1.0",
  "app": "skeleton-wiki",
  "workspaces": [{ "name": "...", "pages": [{ "title": "...", "content": "...", "versions": [...] }] }]
}
```

### Skeleton CRM — CRM Standard v1.0
Exports contacts, companies, deals, pipelines, and activities.
```json
{
  "version": "1.0",
  "app": "skeleton-crm",
  "companies": [...],
  "contacts": [...],
  "pipelines": [{ "name": "...", "stages": [...] }],
  "deals": [...],
  "activities": [...]
}
```

### Skeleton AI — AI Assistant Standard v1.0
Exports sources (metadata only, not embeddings) and conversations with message history.
```json
{
  "version": "1.0",
  "app": "skeleton-ai",
  "sources": [{ "title": "...", "source_type": "...", "config": {...} }],
  "conversations": [{ "title": "...", "messages": [...] }]
}
```

**Note:** The AI standard intentionally excludes embeddings from exports. Embeddings are model-specific and must be regenerated by the importing system through re-ingestion.

## How Skeleton AI Ingests Other Skeleton Docs

Skeleton AI can serve as a knowledge layer for the entire ecosystem by ingesting the source code and documentation of other skeleton apps:

1. **Add a source** pointing to another skeleton's root directory (e.g., `/path/to/skeleton-tasks/`)
2. **Trigger ingestion** — the crawler walks the directory, respecting ignore patterns
3. **Files are chunked** — Markdown files split on headings, code files on function boundaries
4. **Embeddings generated** — Each chunk gets a 384-dimension vector via Ollama
5. **Ask questions** — "How does skeleton-tasks handle drag and drop?" returns relevant code and documentation

This makes Skeleton AI a powerful tool for developers working across the ecosystem, providing instant answers grounded in actual source code.
